# P0.3 - Cross-platform build

The native simulation core now has Windows and Linux CMake presets. Each script
builds the same source and tests against the MuJoCo library inside that checkout's
Python environment. MuJoCo is the physics simulator; none of these checks involve
real motors. The Windows script still locates Visual Studio's compiler tools.

Windows generates an import library for its wheel's DLL and delays loading that
DLL until Python imports MuJoCo. Linux links directly to the wheel's shared
library. Its compiled files record that library directory as a runtime search
path, so the standalone tests and Python extension find the same physics engine.
Rebuild after moving or replacing the Python environment.

Linux compiles the static core as position-independent code, which can be linked
into a Python extension regardless of where the operating system loads it. Both
platforms disable fused multiply-add contraction to preserve the separate
arithmetic operations expected by the existing exact-equivalence checks. The
controller, observation/action layout and comparison tolerances are unchanged.

Git keeps the pinned model XML and license in LF format, preserving their byte
checksums across fresh Windows and Linux checkouts. Generated Linux extensions
are ignored just like Windows extensions.

The Ubuntu workflow installs the pinned dependencies with CPU-only PyTorch,
builds the core, runs pytest and CTest, and runs the standalone C++/Python
comparison. OSMesa supplies rendering without a display. The existing
Windows-only file-sharing reproduction remains skipped on Linux by its original
test condition.

Verification: Windows pytest and CTest passed before and after the change, the
updated Windows script built successfully, and the standalone exact-equivalence
check passed. Local logs are in `build/p0.3/`. Hosted Linux CI is pending; this
slice is not complete until it passes.
This build change does not measure policy quality, latency or hardware behavior.

An interviewer might ask: "How do you prevent the Python and C++ sides from using
different physics libraries?" One-sentence answer: "CMake discovers MuJoCo through
the selected Python environment and links the native targets to that exact
wheel, while shared ownership and exact-equivalence tests check the boundary."
