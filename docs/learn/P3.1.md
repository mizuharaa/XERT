# P3.1: embodiment specifications

An embodiment is the physical arrangement of a robot. Its specification now
declares a MuJoCo model file, ordered joint names, position/speed/acceleration
limits, rest pose, tool sites, source-to-site mapping, IK weights, control rate,
and gripper endpoints. A site is a named point attached to a robot link.
Inverse kinematics (IK) finds joint positions for a desired tool position.

The loader checks dimensions, finite values, unique names, valid bounds, and
rest/gripper positions before loading the model. It then checks that each joint
and site exists and that configured positions stay within the model limits.
Only single-coordinate hinge and sliding joints may be commanded.

Specs use the JSON-compatible subset of YAML, parsed by the standard library.
This deliberately excludes YAML tags, aliases, and unquoted-key syntax; invalid
syntax fails with an explicit message. It needs no added parser dependency.

`assets/xlerobot/bench.xml` is a portable snapshot of the existing `model_xml()`
scene builder, using the same pinned mesh files and original license. The
`xlerobot_left.yaml` name preserves the audit finding: this existing chain is
SO-ARM100-generation geometry, not verified SO-101. The original environment
and its observation/action contract are unchanged. Velocity and acceleration
limits are conservative **simulation configuration**, not measured motor limits.
No hardware safety or performance is claimed.

Tests exercise valid loading and invalid names, dimensions, nonfinite values,
limits, mappings and gripper positions. Existing Python and CTest gates are run
before and after this slice; results are build logs, not robot performance data.

**Interviewer question:** Why put robot details in a file?

**One-sentence answer:** A validated specification lets the same controller use
different joint arrangements without hiding robot-specific assumptions in code.
