# P3.5: webcam controls and a paced simulation loop (partial)

The software is implemented; **live acceptance remains unmeasured**. No webcam
was accessed during implementation. Scripted hand fixtures and a black-image
model smoke check are software checks, not human demonstrations or live latency.

`MotionSource.read()` returns a new timestamped hand frame or `None`. OpenCV
capture and MediaPipe inference run in separate workers, each with a single
latest-value slot. Blocking inference uses MediaPipe's tracking-enabled VIDEO
mode while capture continues draining. Missing or ambiguous hands become missing
motion, so the existing watchdog requests hold and then rest. Capture failures
stop the run and close resources. Only the capture worker releases the camera;
a blocked native read causes a bounded close timeout with worker-owned resources
retained, rather than racing release against read. Images are not saved.
Cleanup attempts both the source and backend, preserves the original failure,
and attaches later cleanup failures as notes. Camera-release failures reach the
worker error channel and cannot turn shutdown into a falsely successful run.

MediaPipe's world landmarks are hand-centered. They describe finger shape and
palm orientation, not global wrist translation. The mapping therefore uses
neutral-relative image XY and a palm-size depth **control proxy**. This is not
metric motion capture: wrist rotation also changes apparent palm size and can
request unreachable targets. Command bounds still apply. Neutral calibration records the palm coordinate basis,
image dimensions, spec/profile hashes and camera/model identity. Gains and axis
conventions are declared settings in `configs/teleop`, not measured accuracy.
Handedness probability is named honestly; unavailable tracking confidence is null.

SO101 uses the existing quaternion-capable IK and pinch-to-gripper mapping; G1
uses both wrists. LEAP's profile maps finger bend changes to named joints and
leaves unmapped spread joints at rest. Profiles contain robot-specific choices;
the controller has no robot-name dispatch. Arbitrary wrist poses may be
unreachable, and these mappings do not guarantee collision-free motion.

The loop separates nominal simulation ticks from real monotonic timestamps.
The safety controller uses nominal time for command limits and real time for
input age. Whole-period overruns abort instead of bursting catch-up commands.
The recorder hook receives post-step state, command, clamp events and stage
timestamps. Unique valid applied frames contribute latency samples; missing
hands and repeated frames do not. The measured endpoint will be host capture
return through simulation step completion, excluding unknown sensor/driver delay.

Setup: create a separate environment, install `requirements-webcam-lock.txt`,
run `python -m scripts.fetch_hand_model`, then `python -m scripts.smoke_hand_model`.
The controller also requires the native core built for that environment's Python
version using the existing platform build script; the model smoke alone does not.
Use `python -m xert calibrate --help` and `python -m xert latency --help` for
explicit camera commands. Choose a fresh output each time; the latency command
preserves traces and an exact hashed calibration snapshot, then appends completed-run metrics to the ledger. Escape on
Windows or Ctrl-C stops the run. No real motor backend is used.

Regression checks: `pytest tests/test_runtime.py tests/test_safety.py
tests/test_webcam.py -q`. The optional webcam test uses a mock capture device.
Remaining acceptance: verify the labeled left/right hand with a known hand in
the actual camera view (Tasks conventions differ from legacy Hands examples).
Daniel supplies a fresh neutral pose and an actual live
`--duration 300` run for each embodiment. Latency: **TBD (not measured)**.

**Interview question:** Why keep two clocks?
**Answer:** Simulation ticks define discrete command limits, while real elapsed
time determines whether a camera observation is stale and how long processing took.
