# P6 prep: SO-101 hardware backend, dry-run only
No motor has moved. `hw-dry-run` opens no serial port and imports no LeRobot
robot or motor code. `xert hw-read` (owner-run, below) opens the bus read-only;
no hardware has been read yet. Hardware numbers: **TBD (not measured)**. No
ledger rows.

**What exists.** `SO101HardwareBackend` implements the same `Backend` protocol
as the MuJoCo backend, but only with `dry_run=True`; `dry_run=False` raises.
`send_targets` takes a target that already passed `SafetyController`. It maps
each sim joint (radians) into motor space: `sign * units_per_rad * q +
zero_offset`. Then it limits the command to the joint map's motor min/max, max
speed and max acceleration, braking with the same stopping rule as
`SafetyController` so it stops at its target without overshoot. It prints and
records the result. Nothing is sent. `read_state` returns the last commanded
targets as a `CommandedState` with `measured=False`; the recorder and the
latency summary refuse such state. The joint map (`configs/hardware/so101_joint_map.yaml`) fills in only
what LeRobot documents: motor names, ids 1-6 in spec order, and units (degrees
for the body, 0-100 for the gripper; `so_follower.py:50-60`,
`config_so_follower.py:42`). Every measured value is TBD. The loader refuses
TBD outside dry-run. In dry-run a TBD joint prints `unmapped` with its sim
target; it is never guessed.
`python -m xert hw-dry-run --spec xert/spec/so101.yaml --map
configs/hardware/so101_joint_map.yaml --clip <clip> --output <new dir>
[--seed-from <read.json>]` runs clip, calibrated mapper, safety layer, hardware
clamp and print, in simulated time. It writes `config.json` and `trace.jsonl`,
both labelled "dry-run, no hardware". The clip calibrates itself, as in P3.6.

**Why dry-run first.** A sign error or a wrong zero offset makes a real arm
slam into its own frame. A dry-run shows the exact numbers that would go to
each motor before any can move. It also proves that the hardware path never
loads the bus code (a test checks the imported modules).

**P6.2 software blockers: closed in slice M (2026-11-17), tested with a fake
bus only.** The backend and the safety layer now share one state.
- (a) E-stop reaches the backend (`f2a3b0f`). On an e-stop tick `run_loop`
  calls `SO101HardwareBackend.hold(t)`, which re-sends the backend's own last
  motor targets at zero velocity. An e-stop on the first tick sends nothing
  and marks that record `emitted: false`. Sim backends have no `hold` and get
  the frozen command, which is already a hold for a position servo.
- (b) The controller tracks the applied command (`e0c0dc6`).
  `SafetyController.observe(applied)` takes what the backend really sent after
  its motor clamp as the controller's state; velocity is between consecutive
  applied samples. `run_loop` calls it only for unmeasured (commanded) state.
- (c) One read-only start pose (`9598718`, `f023bb4`, `e906358`).
  `xert hw-read` reads `Present_Position` once; `hw-dry-run --seed-from` starts
  the backend, the controller and the mapper's calibration model from that
  read, with radians recomputed through the run's own joint map.
- **Owner decision, not built:** feeding the MEASURED `Present_Position` back
  into the controller during motion. Today the controller tracks the applied
  command, not the measured one.

**Owner-only bring-up, in order (P6.1-P6.2, Daniel present, a human on the
power switch from step 1):**
1. LeRobot motor setup (`lerobot-setup-motors`: writes ids and baud rate, one
   motor at a time) and calibration (`lerobot-calibrate`). Calibration runs
   `connect(calibrate=False)`, which calls `configure()`; its
   `torque_disabled()` block turns torque ON when it exits. Torque stays ON
   until `calibrate()` disables it for a new calibration, or until
   `disconnect()` turns it off at the end (the default).
2. Measure the joint map on the real arm: sign, scale, zero offset, limits,
   then choose speed and acceleration limits below the sim ones.
3. Read-only position read: `python -m xert hw-read --port <COMx> --calibration
   <robot.id>.json --output <read.json> [--joint-map <map>]`; compare
   `read.json` with the arm's pose by hand. It refuses a TBD or incompatible
   map before the port opens, and marks a tick at or past either calibration
   bound as `saturated` (`valid_for_seeding: false`).
4. Then one joint at a time, low speed, low torque limit, a human on the
   power switch. Never forward sim actions straight to the motors.

**What `xert hw-read` does on the bus (LeRobot 0.6.1, line numbers in the
installed package).** It builds a bare `FeetechMotorsBus` with the
`so_follower.py:50-60` motor table and makes exactly three bus calls:
- `connect()` (`motors_bus.py:514-528`) opens the port (`_connect`, `:530-541`)
  and runs the Feetech handshake (`feetech.py:155-157`): `_assert_motors_exist`
  pings every id and compares the model number it returns
  (`motors_bus.py:465-502`, `ping` at `:948`), then `_assert_same_firmware`
  reads the firmware major/minor version registers of every id
  (`feetech.py:145-153`, `_read_firmware_version` at `:431-448`).
  `set_timeout()` (`motors_bus.py:693`) only changes the host-side packet timeout.
  The handshake reads; it writes nothing.
- `sync_read("Present_Position", normalize=False)` (`motors_bus.py:1128-1171`)
  reads raw ticks. XERT then applies LeRobot's own `_normalize`
  (`motors_bus.py:854-881`, arithmetic only, no bus I/O) to the same ticks, so
  raw and normalized values come from one acquisition. Range modes clamp to the
  calibration interval first (`:867-873`); degrees do not (`:874-877`).
- `disconnect(disable_torque=False)` (`motors_bus.py:546-562`) closes the port;
  the torque write at `:557-560` runs only when `disable_torque` is true.
It never builds `SOFollower` and never calls `configure`, `write`,
`sync_write`, `enable_torque` or `disable_torque`.

**LeRobot 0.6.1 calls that write to the bus** (avoid them in step 3).
`SOFollower.connect()` (`so_follower.py:92`) may call `calibrate()` and always
calls `configure()`. `configure()` (`:159`) writes operating mode, PID gains and
gripper torque limits, and its `torque_disabled()` block re-enables torque
when it exits (`motors_bus.py:677-691`). Other writers: `calibrate()` (`:115`),
`setup_motors()` (`:173`), `send_action()` (`:205`, `sync_write("Goal_Position")`),
`disconnect()` (torque off by default, `motors_bus.py:547`),
`disable_torque`/`enable_torque` (`feetech.py:291,302`), `write_calibration`
(`feetech.py:268`) and `configure_motors` (`feetech.py:209`).
`lerobot-find-joint-limits` drives the arm. Read-only:
`FeetechMotorsBus.connect()` (open port and ping), `read`, `sync_read`,
`read_calibration`, and `disconnect(disable_torque=False)`.

**Interview question:** Why clamp again in the hardware backend when the
safety controller already limits speed and acceleration?
**Answer:** The safety controller uses sim limits in joint radians; the motor
limiter will use measured, stricter limits in the motor's own units. Since
slice M the controller takes the limiter's output as its state (`observe`), so
the two no longer drift apart.
