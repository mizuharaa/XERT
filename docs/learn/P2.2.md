# P2.2 — Record runtime transitions directly to LeRobot v3

`xert/data/recorder.py` connects to the runtime's `on_step` callback. Initialize
`RuntimeRecorder` with `backend.read_state()` before entering the loop, and use
it as a context manager around `run_loop(..., on_step=recorder)`. It writes one
episode using the actual LeRobot v3 writer. The recorder supports each validated
embodiment spec without robot-specific branches.

An observation is the joint state **before** the action. Runtime callbacks carry
the state **after** the simulator steps, so the recorder retains the previous
state and writes the new one as `xert.next_observation`. Actions are absolute
joint angles in radians after safety clamps. This differs from the legacy NPZ
export's normalized actions; the dataset manifest states the units and alignment.
Velocity means how quickly each joint angle changes.

Capture, landmark, inverse-kinematics (finding joint angles for a target), command
and applied timestamps are stored alongside nominal control and simulator times.
They are separate clock domains. Presence masks distinguish missing data from a
real zero. Tracking confidence remains missing when the source does not provide
it; handedness scores describe left/right classification, not tracking quality.
Clamp flags, event details and source provenance are recorded. Task outcome is
unknown unless actually evaluated; this recorder does not infer success.

Use `load_runtime_dataset(path)` for timing analysis. It returns a real
`LeRobotDataset` with a feature-aware transform preserving declared float64
timestamps. The pinned upstream default transform downcasts floating lists to
float32, losing short intervals on large host clocks. Normal state/action loading
still works through the default reader. LeRobot's derived `timestamp` is frame
index divided by rate, not a measured acquisition timestamp.

Successful exit saves, reloads and checks every frame before publishing a fresh
directory. Failure retains an unpublished `.xert-recording-*` directory with a
flushed JSONL recovery journal; an existing destination is never replaced.
This is one episode per transaction; start/discard UI belongs to P4.

`tests/test_recorder.py` checks real-reader alignment, masks, timestamp precision,
clamps and failure recovery. Run it in the approved LeRobot environment with a
native core built for that Python. `python scripts/record_scripted_runtime.py
--output results/p2.2/<fresh-run>` produces three simulated datasets and appends
round-trip evidence to the ledger. Landmarks and clock are explicitly scripted:
these are neither human demonstrations nor live-latency measurements. Live P3.5
acceptance remains outstanding.

**Interview question:** Why keep both the previous and next state?
**Answer:** A policy must learn which action to choose from what it knew before
acting, while the next state records the action's observed effect.
