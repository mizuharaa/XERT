# P2.3: simulated cameras, rendered after recording

`python -m xert render-cameras --dataset <recording, P2.1 export or P4.1 session> --output <fresh path>`
copies a bench dataset and adds two image features: `observation.images.scene` and
`observation.images.wrist`. These are **MuJoCo renders of the simulated bench, not
real camera data**. No ledger rows, no training result: whether images help a
policy is a later, separate experiment. Result: **TBD (not measured)**.

**Two cameras.** The scene camera is fixed in the world above the far end of the
table, facing the arm and aimed between the block start area and the tray. The
wrist camera is attached to the `Fixed_Jaw` body (the gripper's fixed finger), so
it moves with the hand and looks along the jaw toward the fingertips. Positions, aim points and field of view
live in `CAMERAS` in `xert/data/cameras.py` and are copied into each output's
`xert_cameras.json`. The cameras are added in memory with `mujoco.MjSpec` (MuJoCo's
editable model object). The vendored files are only read and stay checksummed; a
camera has no mass or joint, so the physics and state layout are unchanged.

**Offline, not live.** Rendering during teleop would cost time inside the control
loop and could miss deadlines. The bench's full simulator position vector (`qpos`)
is the six arm joints plus the block's position and orientation, and the tray never
moves. Recordings already store exactly these values (`observation.state` and the
`block.*` entries of `observation.environment_state`; the P2.1 export keeps them in
`observation.state`). The command copies them into `qpos`, runs `mj_forward` to
recompute every body pose, and renders. Each frame is checked: the recomputed
gripper point (`grasp`) and tray position must match the recorded ones within
10 micrometres, or the command stops. It also refuses data whose recorded model
fingerprint differs from the current bench model. What differs from a live render:
the stored state is float32, not float64. Live and rebuilt renders were compared
over scripted episodes; differences are rounding-level (see the slice report).
Contacts are not drawn, so they need no reconstruction.

**Nothing original changes.** Every original column, including LeRobot's
timestamps and indices, must be identical in the output's Parquet table, and
every image must decode through `LeRobotDataset` to exactly the rendered pixels.
Provenance files (`xert_recording.json`, the journal, `roundtrip.json`,
`xert_export.json`) are copied unchanged. A sha256 of every source file is
recorded. The recorder and teleop are untouched, so images are opt-in.

**Format and size.** Images use LeRobot's `image` type: lossless PNG inside the
data Parquet. LeRobot's default `video` type (lossy AV1) is smaller, but lossless
storage lets the round trip compare pixels exactly. The default is 128x128 pixels,
small enough to render and store cheaply. ACT's ResNet-18 image encoder shrinks
images 32 times, so 128 leaves a 4x4 feature grid against 3x3 at 96, and the
small block keeps more pixels in the scene view. `--size` changes it.

**Image ACT.** A test feeds these features to official LeRobot ACT and runs one
training step. P1.4 found that official ACT refuses joint-only input.
The XERT ACT-style model accepts flat state vectors only. Feeding it images
needs an image encoder and changes to its data loader and checkpoint; that is a
separate change.

**Interview question:** Why render after recording instead of during teleop?
**Answer:** The bench's whole scene is fixed by the recorded joint angles and block
pose, so the same images can be rebuilt later, and the live control loop never
pays for rendering.
