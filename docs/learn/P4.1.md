# P4.1: teleoperation collection on the bench (partial)
The software is implemented; **live acceptance remains unmeasured**. Tests use
scripted hands, a scripted clock and scripted key presses, and their datasets say
`scripted`. They are not human demonstrations. No real motors are used.
**Which robot.** The pick-and-place bench (a table, an orange block and a green
tray) exists only in the scene of the older XLeRobot arm, spec `xlerobot_left`.
The Robot Studio SO-101 model has no block or tray, and the native task code
names the XLeRobot joints. So teleoperation runs on `xlerobot_left` and is not
labelled SO-101. Moving the task to SO-101 needs a new scene and a C++ change.
**Success.** `BenchBackend` drives the existing native environment through
`ManipulationEnv`. Each command is an absolute joint target; the backend converts it
to the environment's [-1, 1] action and the core runs 20 physics substeps. The
core's contact rule decides success. The block must have been lifted. Then it must
rest inside the tray, nearly still and not touching the robot, for 12
consecutive control ticks. No new success rule was written.
**Episodes.** Space starts an episode and Space stops it. `d` discards it.
Escape is the emergency stop: the safety layer holds the arm for one tick, and
the session ends. Each kept episode becomes its own LeRobot v3 dataset,
`episode_000000`, `episode_000001`, and so on, through the existing recorder. A
discard deletes the private staging folder, so nothing is written. An emergency
stop keeps the unpublished journal, like any other recorder failure. Success,
timeout or a fallen block ends the episode automatically, and the episode is
saved. Each frame stores `next.success`: whether the task counts as done after
that frame's action (the LeRobot name), and `observation.environment_state`: the
14 native observation entries after the joints (`block.x..qz`, `grasp.x..z`,
`tray.x..z`, `time_fraction`, names from `ManipulationEnv.metadata()`, the P1.4
ACT split). Like `observation.state`, it is the state before that frame's action,
so the P5.3 gate looks every name up from live bench state unchanged. Other
recordings keep their old schema. The manifest records the outcome, how
the episode ended, the bench seed and the calibration. The bench seed is the
kept-episode index, so a discarded attempt is retried with the same block position.
The terminal prints the gripper and block positions once per second. No window
opens unless `--viewer` is given. Then a MuJoCo passive window shows a viewer-side
copy of the bench: each tick copies the joint and block pose into it and syncs, so
dragging in the window cannot move the real block. A test with a real window shows
the recorded data is identical with and without it, and it fails if one sync takes
over a quarter of the 40 ms tick. A slower viewer stops the run through the
existing deadline checks and never makes up time. The test skips without a display.
Escape pressed on the tick an episode ends still quits. Teleop also refuses a
calibration whose grasp is more than 1e-6 m from the bench reset grasp.
**Reach.** `calibrate --bench` ties the neutral hand to the bench reset pose, so
an episode starts without a sweep, and teleop refuses any other calibration.
`configs/teleop/xlerobot_bench.json` maps image left/right to robot sideways
motion, up/down to height, and apparent palm size to forward/back. Orientation
is off because holding the reset gripper angle made the block unreachable. A
test maps scripted hands through calibration and IK to the block, above it, and
the tray. Each needs under a third of the image and at most 1.5x palm size.
**Run it** (Windows console, fresh paths; hold the hand in the upper middle of the view):
`build/venv-teleop/Scripts/python.exe -m xert calibrate --bench --spec xert/spec/xlerobot_left.yaml --profile configs/teleop/xlerobot_bench.json --output build/teleop/neutral.json`,
then `build/venv-teleop/Scripts/python.exe -m xert teleop --viewer --spec xert/spec/xlerobot_left.yaml --profile configs/teleop/xlerobot_bench.json --calibration build/teleop/neutral.json --output build/teleop/session_01`.
**Environment.** `requirements-teleop-<platform>-lock.txt` = the ACT lock plus the
MediaPipe-only webcam pins. NumPy stays 2.2.6: LeRobot needs `<2.3` and MediaPipe
sets no bound. `opencv-contrib-python` is excluded. It and LeRobot's
`opencv-python-headless` both install `cv2`. MediaPipe's hand landmarker never
imports `cv2`, and XERT uses only `VideoCapture` and `cvtColor`, which headless
has (MSMF and DSHOW backends). So `pip check` reports that one missing package.
Build: `uv venv build/venv-teleop --python <Python313>/python.exe`, then
`uv pip sync requirements-teleop-windows-lock.txt --python build/venv-teleop/Scripts/python.exe --only-binary :all:`
(never a plain `pip install -r`, which would add contrib back).
