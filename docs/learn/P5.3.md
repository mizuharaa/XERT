# P5.3: gate experiment harness (software only)
The harness is implemented; **the experiment has not run**. It needs P4.2 human
demos and P5.2's committed `configs/gate.yaml`, and neither exists yet. Tests use
scripted bench sessions, tiny training (seconds), temporary gates and temporary
ledgers. Gate result: **TBD (not measured)**.
**Three conditions.** A trains on all demos. B trains on demos that pass the gate
(`verdict` from P5.1 with the gate.yaml thresholds). C is a random subset of A
with exactly as many demos as B. **Why C exists:** if B beats A, there are two
explanations. The gate may have removed bad demos, or the policy may simply do
better with less (or more uniform) data. C has the same amount of data as B but
no quality selection, so B beating C credits the selection. B beating A only
could mean "less data". C is drawn again for each training seed from
`control_subset_seed`, so it is reproducible and not one lucky draw. C matches
B in demo count, not in frames or gradient steps. A gate on frames or duration
therefore changes B's training volume compared with C; each row and the report
show `train_frames`.
**Protocol** (`configs/gate_experiment.json`, fixed before any demo exists):
three training seeds, each training A, B and C, and every model rolled out on the
same 30 held-out bench seeds (10000-10029). Demo bench seeds are kept-episode
indices, and the run refuses any overlap. A training seed also sets the
train/validation split. Each model gets one ledger row: success rate, Wilson 95%
interval, gate.yaml sha256 and the commit that introduced it.
**Pre-stated "measurable" rule.** For each condition, pool its 90 rollouts and
compute a Wilson 95% interval. B differs measurably from A (or C) only if the two
intervals do not overlap: B above means the gate helped, B below means it hurt,
overlap means no measurable difference. Non-overlap is strict, so a small real
effect can read as "no difference". The models share evaluation states, and the
pooled interval ignores variation between training seeds, so it is approximate;
the report says so. Rollouts bypass the SafetyController (a joint-limit clip
only), the same way for A, B and C.
**Pre-registration in code.** The run refuses when gate.yaml or the experiment
config is missing, outside this repo, uncommitted, or differs from its commit
(including edits hidden by `assume-unchanged`). It also refuses a dirty repo and
an experiment tag that the ledger already holds. Rows record both files' sha256
and commits. Changed thresholds mean a new commit and a new experiment.
**Data rules.** Every episode manifest must say `webcam` or `recorded_human`, and
the per-frame source must agree (the P5.1 check); scripted data is refused.
`results/gate_experiment.md` is written only from ledger rows.
**Training path.** The XERT ACT-style model (P1.3), not official LeRobot ACT.
Official ACT refuses state-only inputs: it needs an image or
`observation.environment_state`, and teleop records joint positions only. The
XERT model accepts any flat state, and `train()`/`load_policy()` take arrays,
so no LeRobot adapter was needed. Actions are scaled to [-1, 1] by the joint limits.
**Features.** Inputs are every `observation.*` feature in the recordings, in
dataset order. The output is `action`. On the bench, each input name is looked
up from live state: `<joint>.pos`, `<joint>.vel`, or a native name such as
`block.x`. An unknown name stops the run before training. Joints only works
today, and adding block/tray features later needs no harness change.
Run (LeRobot env): `python -m xert.eval.gate_experiment --sessions build/teleop/session_01 --output results/p5.3/gate_v1`.
**Interview question:** Why add a random subset the same size as the gated set?
**Answer:** It separates "the gate picked better demos" from "the policy just
trained on fewer demos", because only the selection differs between B and C.
