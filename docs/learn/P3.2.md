# P3.2: general inverse kinematics

Inverse kinematics (IK) finds joint positions that place a robot's named tool
points at desired positions. The new C++ solver accepts the joints, bounds,
weighted tool targets, and optional orientations supplied by a specification.
An orientation is represented by a unit quaternion (four numbers in wxyz order).
It supports multiple simultaneous tool points without robot-specific code.

Damped least squares solves a small linear system at each iteration. Damping
keeps the system solvable near a singularity, where some tool movements cannot
be produced independently. Each update and final joint position is bounded.
The Python wrapper resolves names; native code validates dimensions, finite
values, joint types, limits, and unit quaternions before touching MuJoCo arrays.
It solves on a private state, leaving the caller's simulation unchanged.

The original task-specific expert keeps its exact floating-point operation
order. The general solver is alongside it so existing trajectories retain the
same behavior. Python tests check position and orientation tracking, invalid
inputs and state preservation; the standalone legacy equivalence check also runs.

Unlike the historical XLeRobot asset, `so101.yaml` uses the actual Robot Studio
SO101 model from [MuJoCo Menagerie](https://github.com/google-deepmind/mujoco_menagerie/tree/cda5236f98383f6fbaa4820c6b18dba892cd087f/robotstudio_so101),
with an immutable upstream commit, license and file checksums. `prepare_so101.py`
only adds a named site at the upstream fixed jaw tip and writes a spec whose
bounds intersect the joint and position-actuator limits. Simulation speed and
acceleration bounds are chosen settings, not hardware measurements.

`scripts/measure_ik.py` records every sampled target, solution and position error
and appends mean, percentile and maximum errors to the results ledger. Targets
come from forward kinematics near the rest pose. These measurements establish
local position tracking in simulation; they do not establish global convergence,
collision avoidance, motor tracking, or human-motion retargeting quality.

**Interviewer question:** Does a small IK error guarantee safe motion?

**One-sentence answer:** No; kinematic tracking needs separate motion limits,
collision checks and hardware calibration before a real robot can execute it.
