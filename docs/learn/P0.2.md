# P0.2 - Results ledger

An evidence ledger is a file that gains a new JSON record for each completed
measurement. Existing records are never replaced. `xert ledger show` prints it;
the existing evaluation CLI and HTTP jobs write it through the shared pipeline.

Each evaluation saves its full simulator configuration and report before adding
the ledger row. The row carries a unique ID, UTC time, source commit, dirty-tree
flag, simulation backend, robot identity, exact evaluation seeds, training random
seed when applicable, artifact paths and the measured success rate. Demonstration
seeds identify the collected data; they are not the learner's random seed.

The pinned robot is labelled `xlerobot_left`: its asset declares SO-ARM100, so
calling it SO-101 would claim geometry that has not been established. This is an
explicit extension to the master prompt's example embodiment names. No hardware
result or new observation/action format is introduced.

The evaluator already computes a Wilson interval: a range expressing uncertainty
in a success proportion. The ledger copies it, preserving `null` if repeated
initial states or unverified separation from demonstrations make it unavailable.
A paired benchmark reuses starting seeds across conditions, so each condition and
model gets its existing evaluation row under one experiment ID. There is no extra
pooled score or invented independent sample count.
Review caught rounding at all-failure/all-success Wilson endpoints; the shared
helper now returns exact boundary values so valid evaluations remain recordable.

An operating-system file lock prevents simultaneous processes from interleaving
appends. Before writing, the reader validates the existing lines and rejects a
truncated final line or duplicate ID. Failed writes remain explicit failures;
history is not silently repaired. Tests use a temporary ledger and check real
short simulator runs, missing intervals, training-seed provenance, concurrent
writers and corrupt history. Those checks are not policy-performance evidence.

**Interviewer question:** Why keep this alongside ordinary evaluation reports?

**One-sentence answer:** The ledger makes every published measurement traceable
to its exact source, configuration and report without overwriting earlier results.
