# P0.1 — Establish the starting point

We saved the supplied master prompt, changed the README title from Reach to XERT,
and wrote [the repository audit](../STATE_OF_REPO.md). The running system remains
a simulation-only arm workbench. An embodiment is a robot body and its joint
arrangement; support for different embodiments is still planned.

The existing flow is: choose a scripted or learned action, advance MuJoCo physics,
record the resulting state, save an episode, train, and evaluate. The C++ core
handles physics and the scripted expert. Python handles storage, learning and the
API. Inverse kinematics means calculating joint positions for a desired gripper
pose; the existing solver is tied to this bench task.

We audited before extending because the prompt contains assumptions that would
otherwise become design mistakes. The asset identifies itself as SO-ARM100,
not verified SO-101 geometry. Dataset validation and some command limits already
exist, while a general safety controller and human-demo quality gate do not.
Inspection images exist but are not model inputs. Historical result reports are
separate experiments and do not provide fresh ledger-backed XERT measurements.

The first test attempt caught a Windows checkout issue: converted line endings
changed hashed asset bytes. Restoring the exact pinned bytes made validation work
without changing the model, its manifest or tracked source. Before/after regression
checks and the C++/Python comparison protect the existing behavior; the audit
records the remaining checkout risk and the local environment used.

An interviewer might ask: **Why can the tests pass while the learned controller
still fails?**

**One-sentence answer:** The tests verify implementation contracts, while a successful
learned controller requires separate task rollouts with recorded outcomes.

Try explaining one transition aloud: the current observation selects an action,
the delay queue determines when its joint targets are applied, physics produces
the next observation, and the recorder keeps that ordering. A passing replay
shows those recorded commands reproduce the tested simulation; it says nothing
about physical robot performance.

No learning fix or future middleware was added. Continue with P0.2 only when requested.
